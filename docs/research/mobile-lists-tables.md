# Mobile pass — B. Lists & tables (research 2026-09-06)

Family B of `mobile-brief.md`. Scope: every list/table surface below the phone
breakpoint — `/dossiers` (14 cols + Rappeler selection mode), `/consultation`
(9), `/assignations-chiffrage` (9, bands), `/mes-rappels` (6+5, master-detail),
`/monitoring` (2 wide stat tables), `/utilisateurs`, `/compagnies/[slug]`,
`/tampons`, `/jours-feries`, and the one accepted phone list (`/assignations-atg`
mission cards). Locked rulings (brief §2) are inputs; everything about the phone
layout is decided here with evidence. ✓ = fetched and read; ◦ = known, not fetched.

## 1. Record row — table → row list, not cards

**Findings.**
- NN/g cards ✓: "Cards work best for collections of heterogeneous items"; "When presenting very homogenous items … consider using a standard vertical list of items … to support scannability"; "Card layouts are less scannable than lists … positioning of the individual elements is fixed in size and more predictable for the eye"; "Cards take more space". https://www.nngroup.com/articles/cards-component/
- M3 lists ✓: "Lists should extend edge-to-edge in compact windows. Selecting a list item should open a page with the details"; "Limit supporting text to one to three lines"; "Use gaps for contained lists. Limit dividers to uncontained or complex lists"; single-action lists have "no persistent selected state". https://m3.material.io/components/lists/guidelines — specs ✓: "Targets 48dp", label left padding 16dp, trailing right padding 24dp. https://m3.material.io/components/lists/specs (one/two/three-line heights 56/72/88 dp are in the spec diagrams only ◦).
- Polaris IndexTable ✓: the small-screen `condensed` mode turns the table into a list; ResourceList ✓: items "help merchants find an object and navigate to a full-page representation of it"; shortcut actions "are not shown on small screen devices, so the action must also be accessible in another way". https://github.com/Shopify/polaris (content/components/tables/index-table.mdx, lists/resource-list.mdx)
- uxpatterns.dev ✓: list view when "Only a few attributes matter per item"; table when "Many fields must stay visible together"; "start with List View when the dataset is small and scanning matters more than dense comparison". https://uxpatterns.dev/pattern-guide/table-vs-list-vs-cards
- UX Movement ✓: "You cannot shrink a wide desktop table to get it to fit on a mobile screen. Instead, you must rethink the table design"; "A stacked list is the best UX pattern for mobile tables". https://uxmovement.substack.com/p/stacked-lists-the-best-pattern-to
- Andrew Coyle ✓ (transitional vs priority): stacking "diminishes field comparisons and scan-ability"; priority "should be designed with the most important fields in the first three columns". https://coyleandrew.medium.com/the-responsive-table-44d533fde1e9
- HN "Ask HN: displaying data tables on mobile" ✓: "Pay attention to the first 2-3 columns, the ones the user immediately sees"; "What are the users trying to accomplish? Don't let a prior implementation choice lock down your thinking". https://news.ycombinator.com/item?id=45483080
- Craig Corbin ✓: cards win with "tall elements" (images) and "custom formatting … large text, images, conditional color coding"; tables win for "vertical scanning (i.e. find the lowest price)". https://cwcorbin.medium.com/redux-cards-versus-table-ux-patterns-1911e3ca4b16
- Apple HIG lists ✓: "Keep item text succinct so row content is comfortable to read"; the chevron "reveals the next level in a hierarchy; it doesn't show details about the item". https://developer.apple.com/design/human-interface-guidelines/lists-and-tables
- Adrian Roselli ✓: `display:block` on table parts drops semantics ("screen readers no longer consider this to be a table"); stacked views need explicit roles or, better, real list markup. https://adrianroselli.com/2017/11/a-responsive-accessible-table.html
- Pencil & Paper tables ✓: "Condensed: 40px / Regular: 48px / Relaxed: 56px"; "Use vertical center-align for when the row height varies only slightly (up to 3 lines)". https://www.pencilandpaper.io/articles/ux-pattern-analysis-enterprise-data-tables
- HIG accessibility ✓: 44×44 pt default control size; "about 12 points of padding around elements that include a bezel". Hoober ✓: people "prefer to view and touch the center of the screen"; 7 mm centre targets, ~12 mm at corners. https://www.uxmatters.com/mt/archives/2017/03/design-for-fingers-touch-and-people-part-1.php
- In-app: `/assignations-atg` mission "cards" are ~200 px surfaces with phone/WhatsApp/check-in buttons and a 2-col `dl` — heterogeneous per item (actions differ by state), so a card is right THERE; the dossiers/chiffrage/rappels rows are homogeneous records → list.

**SPEC — record row.** Below the phone breakpoint every `<Table>` of records becomes a `<ul>` of rows (real list markup, no `display:block` tables — Roselli ✓), full-bleed inside the page padding, hairline dividers only, no Card frame, no gaps. Anatomy = the desktop column order collapsed to lines, first-three-columns rule (Coyle ✓, HN ✓): **line 1** identifier `t-mono` 14/600 (left) + the decision figure trailing right (dossiers: ancienneté « 12 j », `Badge danger` past `LATE_AFTER_DAYS`; chiffrage: Délai countdown/chip; rappels: short date + `time` chip today); **line 2** human name `t-body` 14/400 ink, truncated, then « · compagnie » ink-2 (chiffrage: assuré · plaque mono); **line 3** `StatusChip` + `Badge warning` observation truncated to the remaining width (rappels: `StateChip` + « Envoyé par X »). Line 3 is omitted when the row has nothing to say on it (dossiers without observation still show the status chip, so 3 lines is the dossiers default). Heights: 2-line 64 px, 3-line 84 px (M3 72/88 ◦ minus the 16 px padding our chips already breathe), padding 16 px sides / 10 px top-bottom, content vertically centred (P&P ✓). Emphasis budget stays 2 bold cells (addendum ter #2): identifier + decision figure; everything else 400 weight down the ink ladder. No chevron (M3 ✓ lists open details without one; HIG ✓ chevron = hierarchy, and the trailing slot is spent on the figure); no per-row ⋯ (see §10). Whole row = one tap = open (dossier record / chiffrage page / rappel detail); the unread teal bar of Mes rappels stays at `left-0`. Tap target = the whole row (≥ 64 px > 48 dp M3 ✓). Must not: card-per-row for homogeneous records; labels « Statut : » before values (the chip is self-labelling); more than 3 lines; hover-only affordances; `title` tooltips as the only place for the full observation (it lives in the record/detail).

## 2. Frozen-column horizontal table — when it survives

**Findings.**
- NN/g mobile tables ✓: horizontal scrolling is "somewhat acceptable for large tables on mobile screens"; "it must be apparent that there is more data beyond the horizontal fold" — "cut-off elements or arrows"; "dots are … harder for users to notice and understand"; lock headers "for any table that fills more than a single vertical screen"; "the leftmost column … should be locked in place"; number-heavy tables "allow narrower columns"; "You must first create a usable table for a large screen before translating it to a small one". https://www.nngroup.com/articles/mobile-tables/
- NN/g data tables ✓: "Freeze header rows and header columns (if the table is larger than the screen)"; first column "a human-readable record identifier"; "Hiding and reordering columns must be easy". https://www.nngroup.com/articles/data-tables/
- Smashing part 1 ✓: scrollbar approach "useful on complex tables when we want to keep the default table layout and hierarchy"; add `tabindex="0"`, sticky headers, "scrolling shadows" (note: `background-attachment` unsupported on iOS Safari — use an overlay element instead). https://www.smashingmagazine.com/2022/12/accessible-front-end-patterns-responsive-tables-part1/ — part 2 ✓: column-toggle "Give users an option to choose the additional column they'll use for comparison"; off-canvas row detail for "complex enterprise tables". https://www.smashingmagazine.com/2022/12/accessible-front-end-patterns-responsive-tables-part2/
- Brad Frost's pattern list ✓ (Priority Columns, Horizontal Overflow, Data-Table to List, Link to Full-Table). https://bradfrost.github.io/this-is-responsive/patterns.html
- Coyle ✓: overflow's weakness — "users may not know that the table is scrollable and may not see all of the fields".
- Carbon ✓ row sizes 24/32/40/48/64 px; "Column header and row text is always centered in the row"; sorting "located in the column headers". https://carbondesignsystem.com/components/data-table/style/

**SPEC — frozen table (phone).** Legitimate only where the job is column COMPARISON of figures across rows: `/monitoring` (both stat tables), the per-user stats in `/utilisateurs`, `/compagnies/[slug]` amounts, `/jours-feries` (if kept tabular). Never for record queues. Anatomy: `Table` primitive unchanged (44 px rows, small-cap heads, `STICKY_HEAD/STICKY_CELL` on the identifier column), inside a scroll region that is exactly viewport-wide with the right edge deliberately cutting a column mid-word (NN/g ✓ cut-off signal) plus a 24 px right-edge gradient overlay that fades out when `scrollLeft` reaches the end (Smashing ✓; overlay, not `background-attachment`). Phone column set = priority columns (Frost ✓, Coyle ✓): identifier + ≤ 3 figures by default, the rest behind a « Colonnes » bottom sheet (check list, same state as the desktop `Affichage` picker; NN/g ✓ "hiding … must be easy"). Header sticky at the page's sticky offset. Sort stays in the header (Carbon ✓) since headers exist here. Must not: 1 200 px tables panning under a 390 px viewport (today's state); dots as the scroll signal; forced landscape (NN/g ✓); frozen column wider than 40 % of the viewport (cap `min-w` at 9rem → 8rem on phone).

## 3. Search field

**Findings.** HIG searching ✓: "If search is important, give it a primary position in your app or view"; "Use a descriptive placeholder text, a scope bar, or a title". M3 search ✓: bar "at the top of the screen to remain prominent and accessible"; on compact, focusing opens a full-screen search view, "Focus is released when the back icon is selected". Baymard ✓: filters "triggered by a clearly labeled button" that "should remain visible as the user scrolls". Addendum ter A: "Search filters live from the 2nd character". In-app: `/assignations-atg` hides search INSIDE the Filtres sheet — the one place the accepted page deviates from HIG/M3.

**SPEC — search.** One 48 px sticky row directly under the top bar: search `Input` (flex-1, 16 px text, leading icon, trailing × clear when non-empty, placeholder = format cue « Réf., assuré, plaque… »), then the « Filtres » button (§4), then « Trier » (§5) where sort exists. Client-side, as-you-type from the 2nd character with a 150 ms debounce (the snapshot is in memory — no full-screen search view needed; M3's full-screen view is for remote suggestion lists). Enter key blurs the keyboard (`enterkeyhint="search"`). Must not: search behind an icon; search inside the sheet (fix ATG); a second search box in the sheet.

## 4. « Filtres » sheet, count badge, applied chips

**Findings.**
- Baymard filter UI ✓: "Trying to squeeze a sidebar into a mobile viewport doesn't work. Filters should occupy their own layer — either a full-screen overlay or a bottom sheet — triggered by a clearly labeled button"; "Always include a prominent 'Show X Results' button" whose count updates live "so users know what they're committing to before tapping"; "On mobile, an explicit 'Show X Results' apply button is recommended because real-time updates can cause disorienting page refreshes"; "Always surface active filter chips in the main results view"; tap targets "minimum 44×44 pt". https://baymard.com/learn/ecommerce-filter-ui
- Pencil & Paper filtering ✓: three visibility layers — "Keep the active filters visible in their original context (inside the menu)", "Indicate which filters have a selection nested inside (small numerical marker, bold text, background-color)", "Display them in a dedicated 'Applied filters' overview"; "'Clear All' should be possible at the individual filter level and at the global level … a 'Clear All' button is also a reminder that filters are applied"; batch-filtering = "only when all their desired filters have been input, then they would click a global 'Apply' button". https://www.pencilandpaper.io/articles/ux-pattern-analysis-enterprise-filtering
- NN/g bottom sheet ✓: "Include a visible Close (or X) button"; "support the use of Back for dismissing"; grab handle is "easy to ignore" and "prone to swipe ambiguity"; "Avoid displaying lengthy content"; "strongly recommend not using a bottom sheet to replace typical page-to-page user flows". https://www.nngroup.com/articles/bottom-sheet/
- M3 chips ✓: "Filter chips can scroll horizontally to show many options"; selected chip "appends a leading checkmark"; "All chip sets on a page should be either single-select or multi-select". https://m3.material.io/components/chips/guidelines
- NN/g data tables ✓: users must "understand that they are looking at filtered data". Deviniti (mobile-first Jira) ✓: replaced the full filter system with "two or three buttons (20% effort)" that "filter issues from a few thousands to just a couple dozen" — and used native HTML controls. https://deviniti.com/blog/software-engineering/mobile-first-jira-app/

**SPEC — filters.** Trigger: 44×44 outline icon button `SlidersHorizontal` + count badge (surface-3 pill, top-right, count of applied attribute filters, hidden at 0) in the sticky search row (already the ATG spelling). Sheet: bottom sheet at `calc(100dvh - 56px)` for `/dossiers` (7 controls + presets + range = lengthy → full-height with internal scroll, NN/g ✓), 70 vh for pages with ≤ 4 controls; header 48 px « Filtres » + × (NN/g ✓; Android Back closes it — family A); body = one section per filter, `t-label` + control, each section carrying its own selection marker (P&P layer 1–2: value shown + « 1 » pill); date presets Jour/Semaine/Mois/Personnalisé as a single-select chip set (M3 ✓) above the range; sticky footer 64 px = « Réinitialiser » ghost (left, only enabled when something is set) + filled « Afficher 42 dossiers » (right, live count recomputed from the pending filter state — Baymard ✓; the page primary is absent while the sheet is open, so the filled button is lawful). Apply = batch on tap (Baymard ✓, P&P ✓); dismissing via × discards pending changes. Applied-chip row under the search row: 36 px, horizontally scrolling `FilterChip`s (label « Statut : Clôturé », ×), trailing « Tout effacer » ghost when ≥ 2 chips (P&P ✓ reminder); the KPI tiles that set `lateOnly`/`scope` are filters too and MUST appear as chips (NN/g ✓ filtered-data awareness). The per-column filter popovers of the desktop header do not exist on the phone — their state is the same object, edited in the sheet. Must not: live-updating the list behind the sheet; a filter drawer that hides applied filters after closing (P&P ✓ "very common mistake … especially on mobile"); a nested bottom sheet for a select inside the sheet (NN/g ✓ don't stack) — selects inside use the native picker (family C).

## 5. Sort on a phone

**Findings.** Baymard sort types ✓: "a clear label alongside the sort drop-down (e.g., 'Sort By'), with the selected sort type visible by default"; only price "should always be bidirectional". https://baymard.com/blog/essential-sort-types — M2 data tables ✓: sort arrow in the header, tap reverses. Polaris ✓: "Support sorting if the list can be long, and especially if different merchant tasks benefit from different sort orders". Addendum ter A: queues sort by action-needed order, "the fixed order is the sort" (rappels FIFO). Element-specs §2 puts sort in the column header — headers do not exist on a phone row list.

**SPEC — sort.** Only where the desktop has a sort: `/dossiers` (création ↑/↓), `/assignations-chiffrage` (Délai inside bands), `/consultation`. A ghost « Trier : Plus récents » button (icon + CURRENT sort label always visible — Baymard ✓) at the right end of the sticky search row; tap → bottom sheet titled « Trier par » with a single-select radio list, 48 px rows, check trailing, applies on tap and closes (one choice = per-control apply, no footer). Options are named as orders, not columns: « Plus récents / Plus anciens / En retard d'abord » for dossiers; « Délai le plus proche / le plus lointain » for chiffrage. Mes rappels: no sort control (FIFO ruling). Must not: an ↑↓ icon without the label; sort options that are hidden columns; sort inside the Filtres sheet (different frequency class — sort is one tap, filters are a batch).

## 6. Selection mode + bulk actions (« Rappeler »)

**Findings.**
- HIG ✓: "In iOS and iPadOS, people must enter an edit mode before they can select table items".
- M1 selection ✓: "The global gesture to select data is a long-press"; "To toggle an item between selected and unselected states, tap the item"; "To exit selection mode, deselect all items or perform an action on selected items"; "display a check mark and scrim overlapping the item, or its associated avatar". https://material.io/archive/guidelines/patterns/selection.html
- Android CAB ✓: invoked on "touch & hold" or when "the user selects a checkbox"; "displays a contextual action bar … at the top of the screen with action items that affect the selected item(s)"; "visually overtakes the app bar position"; dismissed "when the user deselects all items, taps the Back button, or taps the Done action". https://developer.android.com/develop/ui/views/components/menus
- Carbon ✓: "Once an item … is selected, the batch action bar appears at the top of the table"; exit via "the cancel button on the far right of the bar or deselect all items". M2 ✓: "When a row checkbox is selected, the row should display a background color". NN/g data tables ✓: "a single-click option to Select All".
- Polaris ✓: hides bulk actions < 490 px but "only … when the bulk actions are not essential to the merchant's workflow"; Polaris team: "intentionally does not support bulk action at mobile breakpoints … best on the native … app" (https://github.com/Shopify/polaris-react/discussions/8215) — a product decision, not a usability finding.
- Hoober ✓: centre/bottom reach; HIG ✓ 44 pt.

**SPEC — selection.** Keep « Rappeler » on the phone (gestionnaires "check the phone constantly"; the batch op is real, so Polaris's exemption does not apply). Entry = the header « Rappeler » outline action (explicit mode, HIG ✓) and long-press on any row (M1/Android ✓ shortcut; never the only path). In mode: the top bar becomes a 56 px contextual bar (Android ✓): × left (exits), « 3 sélectionnés » `t-body` 600 tabular centre-left, « Tout sélectionner / Tout désélectionner » ghost right; rows gain a leading 24 px `Checkbox` at 16 px inset (200 ms fade + zoom-in-75 per motion spec; the identifier shifts right 40 px), row tap toggles (M1 ✓), selected rows `bg-accent/40` (M2 ✓). Primary: a 56 px bottom action bar above the 60 px nav bar (thumb zone, Hoober ✓) holding ONE filled « Envoyer à (3) », disabled at 0; the « Envoyer à » dialog is the existing one as a bottom sheet. Exit: ×, Android Back (must exit the mode, not the page — family A), or after send (toast confirms count). Must not: hide the bulk action because the screen is small; a floating checkbox column inside a horizontally scrolling table; two filled buttons (the header's « Nouveau dossier » is hidden in mode, as today).

## 7. « Afficher plus » vs pages vs infinite scroll (live Firestore lists)

**Findings.**
- Baymard/Holst (Smashing) ✓: mobile "Load more" with "15 to 30 products" before the button; "infinite scrolling should never be used for the search results"; > 90 % of load-more sites break Back — "after a user has visited a particular product page … they are taken back to the same spot on that list upon clicking the browser's back button"; footer starvation. https://www.smashingmagazine.com/2016/03/pagination-infinite-scrolling-load-more-buttons/ — Baymard items-loaded ✓: "load only 15–30 products on mobile devices and to load them all at once". https://baymard.com/blog/number-of-items-loaded-by-default
- NN/g infinite scroll ✓: avoid when users need to "Find something specific", "Compare items in a long list", "Inspect only a few items at the top"; Back "will find themselves at the top of the list"; recommends "infinite scrolling with a Load More button". https://www.nngroup.com/articles/infinite-scrolling-tips/
- Polaris ✓: "Paginate when the current list contains more than 50 items". Addendum ter A: queues never paginate with page numbers; cap + « Afficher plus » + visible total.
- Firestore cursors ✓: `limit()` + `startAfter(lastDoc)` on the same `orderBy` for server pages. https://firebase.google.com/docs/firestore/query-data/query-cursors — in-app: the dossiers page holds the whole collection in one live snapshot ("deliberately left uncapped", perf memory) and paginates purely in memory (`rowsPerPage` 10–100 + prev/next).

**SPEC — paging.** Phone lists render a client-side cap: 25 rows initially (Baymard ✓ 15–30), then a full-width 48 px outline « Afficher 25 de plus » with a `t-caption` « 25 sur 312 dossiers » above it (visible total, addendum ter A); no rows-per-page select, no page numbers. Queues ≤ ~100 rows (chiffrage, rappels, ATG) render everything, as today. Live inserts keep working (in-memory snapshot); the cap counts rendered rows, not documents, so new rows above the fold appear immediately. Return from a record restores cap + scroll (`history.state` / `sessionStorage` keyed by route+filters; Baymard ✓ Back-button rule; NN/g ✓). Scroll anchoring on the list container (`overflow-anchor: auto`) so a live insert above the viewport does not jump the reader (Safari lacks it — accept). Must not: infinite scroll (goal-directed queue, NN/g ✓); page-number controls on a phone; server cursor pagination for the dossiers list while it stays a single listener (two listeners per page would replace one).

## 8. Master-detail (Mes rappels) on a phone

**Findings.** M3 list-detail ✓: compact → "Use a single-pane layout … Only one view is visible at a time, either list or detail"; "Back button: Appears in detail view only for single-pane layouts"; "Selected state: Appears only in list view" of two-pane layouts. https://m3.material.io/foundations/layout/canonical-layouts/list-detail — NN/g bottom sheet ✓: "not using a bottom sheet to replace typical page-to-page user flows"; "Avoid displaying lengthy content". Addendum bis: row click SELECTS, « Ouvrir le dossier » is explicit, Traité leaves the queue with an undo toast, 15 px reading size in the panel, ↑/↓/t/Échap keys. In-app: below `xl` the detail is a `Sheet` (side sheet → full-screen below `lg`), with no title (sr-only) and no back affordance beyond the sheet's ×.

**SPEC — master-detail.** Phone = single pane (M3 ✓): the Reçus list is the §1 row list (line 1 ref + short date/`time` chip; line 2 observation 1-line clamp, 500 weight when unread; line 3 `StateChip` + « Envoyé par X »), unread teal bar; tapping a row pushes a full-screen detail (route-addressable `/mes-rappels?id=…` so Back returns to the list at the same scroll — family A owns the top-bar back). Detail: top bar « ‹ Rappels » + ref as title; body = `RappelDetailContent` unchanged (15 px reading size); bottom action bar 56 px: « Marquer traité » tonal + « Ouvrir le dossier » filled. Marquer traité → pop to the list + undo toast (addendum bis); the list shows no selected state (M3 ✓ single-pane). Segments « À traiter (n) / Traités » sit sticky under the search row. Must not: a bottom sheet for the detail (NN/g ✓ page-to-page flow); a detail without its own back; keyboard-hint `Kbd`s on the phone.

## 9. Sticky group headers (bands)

**Findings.** HIG lists ✓: grouped style "uses headers, footers, and additional space to separate groups of data"; plain-style section headers pin while their section scrolls (iOS platform default ◦). NN/g sticky headers ✓: "By using a sticky header you give away some screen real estate on every single page"; partially persistent headers should reappear on scroll-up with a "300–400ms" slide. https://www.nngroup.com/articles/sticky-headers/ — Chiffrage bands are locked (addendum ter #1); ATG groups use `Collapsible` with a 48 px header + « Itinéraire ».

**SPEC — group headers.** Band header = 40 px, `t-label` + count pill (danger pill for En retard, as today), `bg-surface-2` solid (no glass — GPU cost, family F), sticky at the offset below the search row (`top: 56 + 48`), pinned only while its group scrolls (`position: sticky` inside each group wrapper). Collapsible only on ATG (kept). Sticky stack budget on a phone: top bar 56 + search row 48 + band 40 = 144 px, leaving ≥ 60 % of a 844 px viewport for rows; the search row scrolls away on scroll-down and returns on scroll-up (NN/g ✓; the band then pins at 56). Must not: sticky filter chips AND sticky bands AND sticky segments together (pick two: bands + search row); glass on sticky rows.

## 10. Row actions: tap, long-press sheet, swipe

**Findings.** NN/g contextual swipe ✓: "Lack of signifiers makes it unclear where the contextual swipe can be used"; "Most users expect to use contextual swipe to find destructive actions"; "Burying key actions behind a contextual swipe prevents users from discovering them"; "Limit contextual swipe to destructive actions". https://www.nngroup.com/articles/contextual-swipe/ — LogRocket ✓: Gmail archive with "a snackbar … offering an Undo option"; "Allow users to hold down on an item to access additional actions"; "clearly visible icons or buttons next to items" as the alternative; warns against "too many swipe options". https://blog.logrocket.com/ux-design/accessible-swipe-contextual-action-triggers/ — Polaris ✓: shortcut actions hidden on small screens must be "accessible in another way". Carbon ✓: on touch devices the overflow menu is persisted (never hover-only). In-app: dossiers rows carry a hover-revealed ⋯ (Ouvrir, Ouvrir dans un onglet, Workflow, 2 historiques, Supprimer); status/observation cells are click targets for history sheets; chiffrage rows have an observations-count ghost button.

**SPEC — row actions.** Tap = open, always. Long-press (500 ms) on a dossiers/chiffrage row opens an action sheet (bottom sheet, 48 px rows, icons left, « Supprimer » last and red) with the desktop ⋯ items minus « Ouvrir dans un onglet »; the same items exist in the record page's overflow (the visible alternative — NN/g ✓, Polaris ✓), so long-press is a shortcut, never the only path. Status/observation history is NOT a tap target inside a row on the phone (a 20 px chip inside a 64 px row is an ambiguity trap); it stays in the record page. Swipe: at most ONE swipe action app-wide, on Mes rappels « À traiter » rows only — swipe left reveals a full-height `success` panel « Traité » (check icon + label, 80 px reveal, full swipe commits), undo in the toast (LogRocket ✓, addendum bis undo rule); it is a completion, not a destruction, so it is shipped as an OPTION (owner question 4) and must also exist as the detail's button. No swipe on dossiers (delete is admin-only and irreversible). Must not: hover-revealed clusters; a per-row ⋯ that eats 44 px of every line; swipe with two or more actions; a swipe direction that means different things on different pages.

## 11. Loading, empty, disconnected

**Findings.** NN/g skeletons ✓: "The structure of the gray boxes mimics the structure of the final page"; "< 1 second … skeleton screens or spinners aren't necessary"; "under 10 seconds" skeleton; "> 10 seconds" progress bar; never "frame-display skeleton screens". https://www.nngroup.com/articles/skeleton-screens/ — LukeW ✓: "Progress indicators by definition call attention to the fact that someone needs to wait"; skeletons create "the sense that things are happening immediately". https://www.lukew.com/ff/entry.asp?1797 — Carbon ✓: "use skeleton states instead of spinners". NN/g empty states ✓: a system message "at completion of the process (e.g., 'There are no records to display for the selected date range')", educational content, "direct pathways"; "Totally empty states cause confusion about how and whether the system is working". https://www.nngroup.com/articles/empty-state-interface-design/ — Polaris ✓: skeleton on initial load. Project memory: the Firestore ca9 cascade wedges sessions → needs a hard reload.

**SPEC — states.** Skeleton = the §1 row anatomy (2 lines of `Skeleton` bars at the real line positions, 3-line variant on dossiers) × 6, shown only after a 200 ms delay (NN/g ✓ < 1 s rule) and for ≤ 10 s, pulse only; « Afficher plus » appends 3 skeleton rows under the button. Empty: filtered → « Aucun dossier pour ces filtres » + one `tonal` « Réinitialiser les filtres » (the fix, as chiffrage does today); first-use → one filled action if the role can create; inbox-zero (rappels) → the quiet « Tout est traité ». All empties name the state AND the reason (NN/g ✓). Disconnected/stale (listener error or no snapshot for > 30 s after a `visibilitychange`): a 40 px inline `Alert` above the list « Connexion perdue — Recharger » with a real reload button — this is the phone's refresh path (§12). Must not: spinner over an empty list; a skeleton that flashes < 200 ms; a page-level skeleton with no rows in it (NN/g ✓ frame-display).

## 12. Pull-to-refresh — no

**Findings.** Material swipe-to-refresh ✓: indicator "Keep the refresh indicator in view until the activity is completed", "Don't scroll the refresh indicator off-screen". https://m2.material.io/design/platform-guidance/android-swipe-to-refresh.html — practitioner consensus (icons8/ui-patterns via search ◦): automatically updating content "shouldn't display a refresh indicator". "Why you shouldn't implement pull-to-refresh in web apps" ✓: custom PTR fights "the native browser behavior … rendered at the system level", causing "violent page shakes or double loading indicators"; the exception is "inside an App WebView" where "the browser's native toolbar is usually hidden". https://javascript.plainenglish.io/why-you-shouldnt-implement-pull-to-refresh-in-web-apps-and-the-only-exception-fb85e92674a3 — Apple's HIG page for refresh controls is no longer published (404 on fetch); UIKit's `UIRefreshControl` ◦ exists for manual reloads only.

**SPEC — refresh.** No custom pull-to-refresh anywhere: every list is a live `onSnapshot`, so a manual refresh would be theatre and, in the PWA, would double the browser's own PTR. PWA: leave the browser's native PTR alone on list pages (`overscroll-behavior-y: auto`) — it is the hard reload the ca9 memory calls for; set `contain` only inside sheets and the selection mode so a gesture cannot reload mid-task. Capacitor build (no browser PTR): the §11 stale/disconnected banner with « Recharger » + an « Actualiser » item in the profile overflow are the reload paths. Must not: a spinner that pulls down on a list that already updates itself; PTR inside a bottom sheet.

## 13. Contradictions and how I resolved them

1. **Cards (ATG) vs rows (everything else).** NN/g/M3 favour lists for homogeneous records; the accepted ATG page uses cards. Resolved by the heterogeneity test: a mission card carries state-dependent actions (call, WhatsApp, en route, check-in) and a 2-col address block — heterogeneous → card stays; dossiers/chiffrage/rappels rows carry the same fields every time → row list.
2. **Chevron: HIG says use one for hierarchy; M3 opens details without one; element-specs §3 says chevron OR ⋯.** Resolved: none — the trailing slot carries the decision figure, the whole list is uniformly tappable, and the ⋯ moved to long-press + record page.
3. **Sort in the column header (§2/§3) vs no headers on a phone.** Resolved: an explicit labelled « Trier » control only where a sort exists; queues keep their fixed order.
4. **Polaris drops bulk actions < 490 px vs NN/g's batch-action mechanism.** Polaris frames it as an essentiality test; Rappeler is essential → kept, with the Android CAB anatomy.
5. **Baymard sticky filter button vs NN/g sticky-header cost.** Resolved with the partially-persistent search row (hides on scroll-down, returns on scroll-up) and a strict 144 px sticky budget.
6. **Element-specs §2 says "filters never inside the table header"; the desktop dossiers page has per-column filter popovers.** Not re-litigated for desktop; on the phone the sheet is the single filter surface and the column popovers vanish with the columns.
7. **Selects inside a bottom sheet vs "don't stack sheets".** Resolved by using native pickers inside the Filtres sheet (family C decides the control; this family only forbids a nested custom sheet).
8. **Load more (Baymard, 15–30) vs "show all ≤ 100" (addendum ter A).** Both kept: queues ≤ 100 render all; the open-ended dossiers/consultation lists cap at 25 with « Afficher plus ».
9. **`lg` = 1024 single breakpoint (brief) vs M3 compact < 600.** For this family: row list below `md` 768 px; frozen table + « Colonnes » sheet from 768 to 1023 (a 9-col table pans ~1.5× there, which is tolerable with a frozen identifier; a 14-col one still needs the picker). Family A owns the final number.

## 14. Do-not list

- No desktop `<Table>` panning under a phone viewport for record lists; frozen tables only for figure comparison (§2).
- No cards for homogeneous records; no boxes inside rows; no labels before self-labelling chips.
- No chevron + ⋯ + figure fighting for the trailing slot; no per-row ⋯ on the phone.
- No hover-revealed anything; no `title` tooltips as the only path to content.
- No live-filtering behind the Filtres sheet; no filter state that is applied but not shown as a chip (KPI tiles included).
- No stacked bottom sheets; no grab handle as the only dismissal; no sheet for the rappel detail.
- No sort icon without the current-order label; no sort options inside the Filtres sheet.
- No page numbers, no rows-per-page select, no infinite scroll on a phone.
- No hiding « Rappeler » because the screen is small; no two filled buttons in selection mode.
- No swipe actions beyond the single optional « Traité »; never a swipe that deletes.
- No spinner over a list; no skeleton < 200 ms; no frame-only skeleton.
- No custom pull-to-refresh; no `overscroll-behavior: contain` on the page scroller of the PWA.
- No glass on sticky band/segment rows; sticky stack ≤ 144 px.
- No density switch on the phone (one density: 64/84 px rows); no `data-density=compact` below `md`.
